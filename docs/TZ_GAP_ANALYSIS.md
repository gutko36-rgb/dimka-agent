# Сверка проекта с ТЗ «Личная система Telegram-агентов»

Дата проверки: 2026-11-10  
Исходная рабочая база: `main`  
Рабочая ветка: `work/complete-tz-v1`

## Принципы, которые нельзя нарушать

1. Один главный Telegram-интерфейс; специализированные агенты — внутренние модули.
2. Supabase остаётся источником данных, Telegram — интерфейсом.
3. Существующие проекты, базы, Google Apps Script и старые боты не удалять и не объединять без отдельного решения.
4. Не считать действие выполненным до подтверждения фактического результата.
5. Не сообщать об успешной записи, пока база не подтвердила её.
6. Критические изменения (удаление записей, проектов, таблиц, изменение схемы) требуют подтверждения.
7. Секреты только в локальном `.env`; в Git допускается только `.env.example`.

## Выявленные технические факты

- Репозиторий содержит `README.md` и один крупный `bot.py`; в проверенной версии файл около 195 КБ.
- Используемые таблицы: `profiles`, `conversations`, `memories`, `daily_surveys`, `analytics_reports`, `finance_transactions`, `finance_payments`, `finance_purchases`, `agent_projects`, `agent_project_items`.
- В `finance_transactions` пока нет поля связи с проектом и нет ключа идемпотентности Telegram-сообщения.
- Финансовые записи в текущем README создаются командами `/expense` и `/income`; обычная фраза «потратил 500» намеренно не записывается.
- RLS включён на таблицах публичной схемы. В `pg_policies` нет политик. При RLS без политик обычный клиентский доступ закрыт; серверный service-role/secret key обходит RLS. Поэтому приложение обязано хранить этот ключ только на сервере и не отдавать его пользователю.
- В текущей проверке не выполнялись записи/удаления в Supabase и не менялась схема.

## Приоритет реализации

### P0 — надёжность и безопасность

- Проверить локально, что `SUPABASE_KEY` — серверный service-role/secret key; сам ключ не отправлять в чат и не коммитить.
- Добавить проверяемые тесты доступа, парсинга и критических действий.
- Добавить идемпотентность входящих Telegram updates для финансовых и других записывающих операций.
- Все выборки/изменения пользовательских данных должны фильтроваться по `telegram_id`.
- Для опасных действий сохранять подтверждение и проверять владельца объекта повторно непосредственно перед записью.

### P1 — первая законченная версия по ТЗ

- [x] Свободная русская фраза -> структурированный черновик одной или нескольких финансовых операций.
- [x] При неоднозначности задавать уточнение; для нескольких операций показывать сводный предпросмотр.
- [x] Запись доходов/расходов с датой, категорией, описанием и опциональной связью с проектом.
- [x] Идемпотентная запись, проверка результата и итоги по данным Supabase.
- [x] Базовые вопросы обычным языком по категориям, проектам и периодам; цифры считаются по строкам Supabase.
- [ ] Учёт долгов, прогноз остатка, анализ бюджета и планирование распределения денег.
- Проектный агент: проект, заметки, ссылки, этапы/задачи, сроки, история; расходы проекта должны быть связаны с проектом.
- Общий диспетчер намерений с явными границами полномочий агентов.

### P2 — расширение

- Отдельный рабочий агент с отдельным источником данных и правами.
- Агент образа жизни: привычки, цели и ежедневные записи как отдельные сущности, не только память ИИ.
- Приём голосовых сообщений, фото и документов с безопасной обработкой.
- Настраиваемый реестр агентов и таблиц с минимальными правами.
- Аудит действий агентов.

### P3 — эксплуатация

- Разделение монолита на модули без изменения поведения.
- Тестовый запуск на Windows и инструкция восстановления.
- Docker/Compose, VPS в согласованном бюджете 500–1000 ₽/мес. только после локальной стабилизации.
- Закрытая веб-панель после стабилизации API и модели прав.

## Что не следует делать сейчас

- Не создавать параллельную новую базу «на всякий случай».
- Не переносить и не объединять три существующих Supabase-проекта.
- Не менять политики RLS наугад: сначала подтвердить серверный ключ и модель доступа.
- Не переносить на VPS до прохождения тестов на Windows.
- Не давать ИИ прямой произвольный SQL-доступ или право удалять таблицы.

## Ограничения проверки

Код и схему можно изучить через подключённые GitHub/Supabase-инструменты, но для полноценного запуска требуются локальные секреты и доступ к Telegram/Groq/Todoist. Эти значения не следует публиковать в чате. До их локальной проверки нельзя честно заявить, что бот запущен end-to-end.
