# Межботовая очередь: первый клиентский модуль

## Что уже есть

Файл bot_queue.py — отдельный модуль для отправки, чтения и обновления записей в bot_messages. Он не импортируется в bot.py и не меняет запуск Димки.

## Обязательное условие безопасности

BotQueueClient должен получать Supabase client, аутентифицированный как конкретный бот отдельным JWT. Нельзя передавать ему client, созданный с service_role / secret key. Локальные проверки в Python не являются защитой доступа: окончательную изоляцию обеспечивает RLS в Supabase.

Существующий Димка пока использует SUPABASE_KEY как серверный ключ для своей текущей базы. Это не меняется в данном этапе. Перед подключением второго бота нужно выдать ему отдельную Auth identity и JWT, а затем проверить, что он может читать только адресованные ему сообщения.

## Методы

- enqueue(...) — создаёт задачу/событие с sender ID из BotIdentity, адресатом, типом, JSON payload и idempotency key.
- fetch_inbox(limit=20) — читает только pending-сообщения, адресованные этому боту и уже доступные по времени.
- update_status(...) — обновляет статус и processing metadata только для сообщения, адресованного этому боту.

Дублирование (from_bot_id, idempotency_key), проверка активности адресата и ограничения RLS обеспечиваются схемой БД, а не этим модулем.

## Ограничения текущего этапа

- SQL из docs/sql/MULTI_BOT_QUEUE_PROPOSAL.sql ещё не применён в Supabase.
- Модуль не подключён к bot.py и не выполняет polling.
- Нет автоматического захвата задачи с блокировкой строки; для параллельных worker-процессов понадобится атомарная RPC-функция.
- Нет второго Telegram-бота, токенов или Auth identities.
- Тесты используют поддельный Supabase-клиент и проверяют формирование запросов, а не реальную базу/RLS.

## Локальная проверка на Windows

Из корня репозитория после переключения на ветку PR:

    python -m py_compile bot_queue.py
    python -m unittest tests.test_bot_queue -v

Ожидаемый результат: 10 tests ... OK. Это не запускает Telegram и не меняет Supabase.
