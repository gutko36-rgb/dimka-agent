# Архитектура нескольких Telegram-ботов

Статус: архитектурное решение, этап 1. Это документирует направление развития; сам по себе не подключает новых ботов и не меняет поведение работающего Димки.

## Цель

`dimka-agent` — первый специализированный бот в расширяемой системе. В дальнейшем появятся другие боты с отдельными ролями, Telegram-токенами и ограниченными полномочиями. Они должны обмениваться задачами и результатами, не дублировать работу и не обходить подтверждения владельца.

## Telegram-группа

Общая группа для видимого взаимодействия:

- Chat ID: `-1004326591308`
- Ссылка: https://web.telegram.org/k/#-4326591308
- Переменная конфигурации: `BOT_COORDINATION_CHAT_ID`

Группа используется для сообщений, которые полезно видеть человеку: уведомлений, итогов, запросов на решение и обсуждений.

### Ограничение Telegram

Telegram Bot API не доставляет ботам сообщения, отправленные другими ботами, как обычные входящие сообщения. Поэтому нельзя строить автоматический обмен бот↔бот на чтении сообщений этой группы. Отключение privacy mode не устраняет это ограничение.

Следствие: группа — интерфейс и журнал для человека, но не транспорт межботовых команд.

## Канал машинного обмена

Для автоматического взаимодействия используется общий backend (первоначально Supabase), а не пересылка сообщений в Telegram.

Логическая модель сообщения/задачи:

- `message_id` — уникальный идентификатор;
- `task_id` — идентификатор задачи или цепочки;
- `from_bot`, `to_bot` — идентификаторы отправителя и получателя;
- `message_type` — `task`, `result`, `status`, `event`, `approval_request`;
- `payload` — структурированные данные с версией схемы;
- `created_at`, `expires_at` — время создания и срок действия;
- `status` — `pending`, `processing`, `completed`, `failed`, `cancelled`.

Это целевая модель, не готовая схема БД. Перед внедрением нужно отдельно согласовать SQL-миграцию, RLS/policies, правила доступа и резервное копирование.

## Правила безопасности и маршрутизации

1. У каждого бота собственный Telegram token и стабильный внутренний `bot_id`. Токены никогда не передаются другим ботам и не попадают в общие сообщения.
2. Каждый бот получает только необходимые права и данные. Общая БД не означает общий неограниченный доступ.
3. Межботовая задача адресуется конкретному `to_bot`; широковещательные сообщения должны быть редкими и явно типизированными.
4. Обработчик проверяет отправителя, адресата, версию схемы, срок действия и уникальность `message_id`.
5. Повторная доставка не должна повторять побочные эффекты: обработка идемпотентна.
6. Бот не исполняет команды из обычного текста группы как доверенные инструкции. Владелец и его разрешённые действия проверяются отдельно.
7. Финансовые операции, изменение задач и другие внешние действия, требующие подтверждения, остаются за явным подтверждением владельца. Другой бот не может подтвердить их вместо него.
8. Защита от циклов строится на маршрутизации, `task_id`, лимите глубины/числа переходов и идемпотентности, а не на надежде, что боты перестанут отвечать друг другу.
9. Секреты хранятся в переменных окружения/secret store. В Telegram-группу не отправляются ключи, персональные данные и содержимое закрытой памяти.

## Роли компонентов

- Специализированные боты: выполняют ограниченные доменные задачи.
- Общий backend: хранит задания, результаты, статусы и минимальный общий контекст.
- Диспетчер/оркестратор (позже): выбирает исполнителя, контролирует тайм-ауты, повторы и эскалацию владельцу.
- Telegram-группа: показывает человеку события и запросы на решение.

На первом этапе отдельный постоянно работающий оркестратор не обязателен: можно начать с таблицы очереди и небольшого общего модуля обмена, когда появится второй бот.

## План внедрения

1. Зафиксировать протокол, роли и модель доверия (этот документ).
2. Подготовить общий модуль конфигурации и идентификации ботов, не меняя поведение текущего бота.
3. Согласовать и добавить очередь сообщений/задач в Supabase отдельной миграцией с RLS и проверками доступа.
4. Подключить второго бота в режиме ограниченного пилота.
5. Добавить диспетчеризацию, повторные попытки, журналирование и мониторинг.
6. Подключать следующие роли по одной, с отдельными тестами и правами.

## Текущие границы

- Этот этап не создаёт таблиц и не применяет миграций в Supabase.
- Не добавляет токены других ботов и не меняет текущий polling.
- Не публикует сообщения в группу и не меняет поведение работающего экземпляра.
- `BOT_COORDINATION_CHAT_ID` пока является зарезервированной настройкой для будущего подключения.


## Общий модуль идентификации (этап 2)

В репозитории добавлен независимый модуль `bot_identity.py` с неизменяемой структурой `BotIdentity` и функцией `load_bot_identity()`. Он читает только публичные идентификаторы и параметры видимых уведомлений:

- `BOT_ID` — стабильный машинный идентификатор (по умолчанию `dimka`);
- `BOT_ROLE` — роль специализированного бота (по умолчанию `personal_assistant`);
- `BOT_DISPLAY_NAME` — отображаемое имя (по умолчанию `Димка`);
- `BOT_COORDINATION_CHAT_ID` — необязательный отрицательный ID группы.

Модуль не читает токены, не создаёт Telegram-клиент, не обращается к Supabase и не выполняет сетевых действий. Его можно импортировать будущими ботами независимо от основного приложения. Отсутствие настройки группы означает `None`; идентификаторы и числовой chat ID валидируются. Переменные добавлены в `.env.example` с безопасными значениями по умолчанию.

На этом шаге `bot.py`, polling и работающий экземпляр Димки намеренно не меняются: модуль подготовлен для последовательного подключения каждого бота в отдельном изменении с собственными тестами.
