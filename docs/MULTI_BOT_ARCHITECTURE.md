# Архитектура нескольких внутренних агентов

Статус: схема очереди развернута; finance worker прошёл реальный smoke test; основной Telegram runtime Димки автоматически забирает и доставляет адресованные ему результаты. Доменные handlers специализированных workers и полная диспетчеризация ещё в работе.

## Цель

`dimka-agent` — единственный основной Telegram-интерфейс. Специализированные агенты — внутренние workers с отдельными логическими ID, ролями и ограниченными полномочиями; им не нужны отдельные Telegram-токены или polling. Они обмениваются задачами и результатами через backend, не дублируют работу и не обходят подтверждения владельца.

## Telegram-группа

Общая группа для видимого взаимодействия:

- Chat ID: `-1004326591308`
- Ссылка: https://web.telegram.org/k/#-4326591308
- Переменная конфигурации: `BOT_COORDINATION_CHAT_ID`

Группа используется для сообщений, которые полезно видеть человеку: уведомлений, итогов, запросов на решение и обсуждений.

### Ограничение Telegram

Telegram Bot API не доставляет ботам сообщения, отправленные другими ботами, как обычные входящие сообщения. Поэтому нельзя строить автоматический обмен бот↔бот на чтении сообщений этой группы. Отключение privacy mode не устраняет это ограничение.

Следствие: группа — интерфейс и журнал для человека, но не транспорт межботовых команд.

## Канал машинного обмена

Для автоматического взаимодействия используется общий backend (первоначально Supabase), а не пересылка сообщений в Telegram.

Логическая модель сообщения/задачи:

- `message_id` — уникальный идентификатор;
- `task_id` — идентификатор задачи или цепочки;
- `from_bot`, `to_bot` — идентификаторы отправителя и получателя;
- `message_type` — `task`, `result`, `status`, `event`, `approval_request`;
- `payload` — структурированные данные с версией схемы;
- `created_at`, `expires_at` — время создания и срок действия;
- `status` — `pending`, `processing`, `completed`, `failed`, `cancelled`.

Эта модель реализована миграцией `20261110035645_multi_bot_queue` в Supabase. Таблицы `bot_registry` и `bot_messages`, индексы, RLS-политики и атомарная функция claim уже созданы. Перед запуском специализированных workers необходимо выдать им отдельные Supabase Auth identities с доверенным `app_metadata.bot_id` и JWT.

## Правила безопасности и маршрутизации

1. Telegram token есть только у главного Димки. Каждый внутренний агент имеет собственный стабильный `bot_id` и отдельную Supabase Auth identity/JWT с минимальными правами; Telegram token ему не выдаётся.
2. Каждый бот получает только необходимые права и данные. Общая БД не означает общий неограниченный доступ.
3. Межботовая задача адресуется конкретному `to_bot`; широковещательные сообщения должны быть редкими и явно типизированными.
4. Обработчик проверяет отправителя, адресата, версию схемы, срок действия и уникальность `message_id`.
5. Повторная доставка не должна повторять побочные эффекты: обработка идемпотентна.
6. Worker не исполняет команды из обычного текста Telegram-группы: он принимает только структурированные задачи из очереди. Владелец и разрешённые ему действия проверяются главным Димкой отдельно.
7. Финансовые операции, изменение задач и другие внешние действия, требующие подтверждения, остаются за явным подтверждением владельца. Другой бот не может подтвердить их вместо него.
8. Защита от циклов строится на маршрутизации, `task_id`, лимите глубины/числа переходов и идемпотентности, а не на надежде, что боты перестанут отвечать друг другу.
9. Секреты хранятся в переменных окружения/secret store. В Telegram-группу не отправляются ключи, персональные данные и содержимое закрытой памяти.

## Роли компонентов

- Специализированные внутренние агенты/workers: выполняют ограниченные доменные задачи без собственного Telegram-интерфейса.
- Общий backend: хранит задания, результаты, статусы и минимальный общий контекст.
- Диспетчер/оркестратор (позже): выбирает исполнителя, контролирует тайм-ауты, повторы и эскалацию владельцу.
- Telegram-группа: показывает человеку события и запросы на решение.

На первом этапе отдельный постоянно работающий оркестратор не обязателен: можно начать с таблицы очереди и небольшого общего модуля обмена, когда появится первый внутренний worker.

6. Подключать следующие роли по одной, с отдельными тестами и правами.

## Диспетчер намерений (этап 5)

Модуль `intent_dispatcher.py` детерминированно направляет входящее сообщение в один из внутренних обработчиков:
- `finance`: финансовый черновик или read-only финансовый вопрос;
- `projects`: запрос к проектному агенту;
- `assistant`: обычный диалог и память.

Решение содержит agent_id, action, capability и политику подтверждения. Реестр политик разрешает специализированным агентам только чтение и подготовку черновиков. Ни один агент не получает прямое право записи, удаления, произвольного SQL или обхода подтверждения. Финансовые черновики требуют подтверждения; проектный обработчик сам обязан показать подтверждение перед записью.

Диспетчер не обращается к БД и не вызывает внешние API. Он выбирает обработчик; фактическое действие остаётся в главном Telegram-приложении.

## Runtime очереди (этап 4)

В репозитории подготовлен универсальный `bot_worker.py`:
- worker атомарно получает только адресованные ему `task`-сообщения;
- выбирает обработчик по `payload.task_type`;
- возвращает структурированный `result` отправителю;
- использует стабильный idempotency key, чтобы повторная обработка не создавала дублирующие ответы;
- не выполняет внешние побочные действия. Изменения данных, отправка уведомлений и финансовые операции остаются за главным Димкой и требуют отдельной проверки/подтверждения владельца.

Главный бот автоматически забирает `result`-сообщения через отдельную RPC `claim_bot_results_for_primary`, которая доступна только `service_role` и выбирает исключительно ответы `to_bot_id='dimka'`. Polling выполняется через Telegram JobQueue раз в 5 секунд. После успешной отправки в личный чат статус меняется на `completed`; при временной ошибке сообщение остаётся повторно доступным после истечения lease. Это не смешивает задачи worker и ответы основному боту.

На этом этапе модуль является библиотекой обработки одной пачки (`run_once`), а не постоянно работающим сервисом. Он ещё не подключён к `bot.py`, не имеет доменных handlers и не использует реальные Supabase Auth identities. Подключение конкретного worker выполняется отдельным этапом после проверки JWT/RLS на development Supabase.

## Текущие границы

- Схема очереди уже применена в Supabase; миграция хранится в `supabase/migrations/20261110035645_multi_bot_queue.sql`.
- Для finance worker создана отдельная Supabase Auth identity/JWT; остальные специализированные identities создаются по мере подключения агентов.
- Результатный inbox подключён к `bot.py`; специализированные worker-процессы по-прежнему запускаются отдельно и не используют Telegram polling.
- Finance worker пока содержит только `diagnostics.echo`; реальные финансовые read/draft handlers ещё не подключены.
- Telegram polling и production-поведение главного Димки не менялись.
- `BOT_COORDINATION_CHAT_ID` остаётся каналом видимых человеку уведомлений, а не транспортом задач.


## Общий модуль идентификации (этап 2)

В репозитории добавлен независимый модуль `bot_identity.py` с неизменяемой структурой `BotIdentity` и функцией `load_bot_identity()`. `bot_id` обозначает логического агента, а не отдельного Telegram-бота. Он читает только публичные идентификаторы и параметры видимых уведомлений:

- `BOT_ID` — стабильный машинный идентификатор (по умолчанию `dimka`);
- `BOT_ROLE` — роль специализированного бота (по умолчанию `personal_assistant`);
- `BOT_DISPLAY_NAME` — отображаемое имя (по умолчанию `Димка`);
- `BOT_COORDINATION_CHAT_ID` — необязательный отрицательный ID группы.

Модуль не читает токены, не создаёт Telegram-клиент, не обращается к Supabase и не выполняет сетевых действий. Его можно импортировать внутренними workers независимо от основного приложения. Отсутствие настройки группы означает `None`; идентификаторы и числовой chat ID валидируются. Переменные добавлены в `.env.example` с безопасными значениями по умолчанию.

На этом шаге `bot.py`, polling и работающий экземпляр Димки намеренно не меняются: модуль подготовлен для последовательного подключения каждого бота в отдельном изменении с собственными тестами.
