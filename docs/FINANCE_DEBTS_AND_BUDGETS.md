# Учёт долгов и бюджеты

## Модель долга

Каждый долг принадлежит одному Telegram ID и имеет направление:
- `owed_by_me` — я должен контрагенту; погашение записывается как расход;
- `owed_to_me` — контрагент должен мне; возврат записывается как доход.

У записи есть контрагент, название, исходная сумма, остаток, срок, статус и заметка. Частичное погашение не закрывает долг; нулевой остаток переводит его в `paid`.

## Атомарное погашение

Операция `record_finance_debt_payment`:
1. Проверяет владельца и блокирует строку долга.
2. Проверяет сумму и статус.
3. Создаёт связанную финансовую транзакцию (expense или income).
4. Создаёт запись погашения.
5. Уменьшает остаток и меняет статус.
6. Возвращает один результат.

Все действия выполняются одной транзакцией PostgreSQL. Повтор того же `source_update_id` возвращает прежний результат и не списывает сумму повторно. Повторное использование того же update ID с другими параметрами отклоняется.

## Бюджеты и распределение

- `finance_budgets` хранит лимит категории на первый день месяца.
- `finance_budget_weights` хранит веса категорий, которые пользователь сам задаёт для распределения остатка.
- `finance_planning.py` рассчитывает остаток и распределение на Decimal.
- Нулевой лимит допустим и показывает любой расход как перерасход.

## Безопасность

- Все таблицы имеют `telegram_id`.
- Внешние роли `anon` и `authenticated` не получают доступ.
- Запись и RPC доступны только серверному `service_role`; ключ остаётся только на сервере.
- Код главного бота обязан фильтровать все чтения/изменения по Telegram ID.
- Погашение долга связано с транзакцией по составному ключу владельца, чтобы не прикрепить чужую транзакцию.

## Статус

SQL находится в `docs/sql/FINANCE_DEBT_BUDGET_PROPOSAL.sql` и проверяется на disposable PostgreSQL 17. Он не применён к рабочему Supabase. Telegram-команды и интеграция с реальными данными будут отдельным этапом после проверки и согласования схемы.
